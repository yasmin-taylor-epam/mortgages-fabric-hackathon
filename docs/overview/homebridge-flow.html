How one early warning becomes one human action

HomeBridge customers sometimes leave for another lender just before their fixed-rate deal ends. This flow scores each mortgage 90 days before the deal ends, watches live portal activity, and gives one servicing adviser one case to look at. A customer who needs payment help goes to trained support first, whatever the score.

The ten stops in order

Step numbers match the blueprint page. History and live paths only meet at step 9.

  1. 1

    Load raw exports

    Pipelines load dated account, payment, transfer-request and servicing exports into raw Lakehouse tables.

    Data and replay · pipelines/

  2. 2

    Freeze feature snapshots

    Notebooks check keys and ledger history, then build clean histories and one frozen snapshot per mortgage, deal cycle and cutoff.

    Notebooks · shared

  3. 3

    Train the models

    One model estimates refinancing risk. One clustering model groups behaviour. MLflow records versions and feature signatures.

    Models and evaluation

  4. 4

    Publish Gold tables

    Scores, segments and evidence references land in Gold Delta tables. A completed-run marker makes them eligible. Power BI reads them in Direct Lake mode.

    Dashboard and action · reports/

  5. 5

    Replay live events

    Eventstream replays a renewal-portal fault into Eventhouse. Each event keeps its original ID and timestamps.

    Data and replay · kql/

  6. 6

    Read the journey

    KQL finds three patterns: stages and portal errors in order, days stuck at one stage, and retries after a software error.

    Data and replay · kql/

  7. 7

    Add account context

    A pipeline copies versioned account context and finished score summaries into Eventhouse. KQL joins them with accepted live events.

    Data and replay · pipelines/

  8. 8

    Stage the journey results

    A separate pipeline copies cutoff-filtered journey results into Lakehouse staging tables, for the notebooks to combine with dated history.

    Pipelines · shared

  9. 9

    Score on a schedule

    A pipeline scores and assigns segments on a schedule. For the replay, the team also starts one run by hand. A failed run leaves the last score marked stale.

    Models and evaluation · pipelines/

  10. 10

    Create one review case

    Activator and Power Automate create an internal case for one adviser in a secured SharePoint list. The writer checks payment-support needs first. A repeat write reads the existing case.

    Dashboard and action · action/

Rules that must hold

These come from the blueprint's build specification. The demo must pass them.

INV-1An active payment-support request goes to trained servicing staff first, whatever the churn score.
INV-2Features use only data known at the checkpoint. Both occurred_at and ingested_at must be at or before cutoff_at.
INV-3At most one open review case per mortgage_id + cycle_id + action_family.
INV-4An unknown or incomplete refinancing outcome gets no label. It never counts as retained.
INV-5risk_updated fires only after a scoring run succeeds. A failed run leaves the last score marked stale.
INV-6The prototype sends no customer messages and makes no rate or credit decisions.
Failure cases the demo must pass (T01 to T07)
IDCaseExpected result
T01The same eligible event is replayed.One review case for the same case key.
T02An unknown account or a conflicting borrower mapping arrives.The record goes to quarantine.
T03The payment feed is stale or missing.The view flags the feed as stale. Missing is not zero arrears.
T04A payment is reversed.Review and rescoring start. The audit record stays.
T05A scoring run fails.Last score marked stale. Live view still updates. No new risk_updated event. Service alerts stay independent.
T06A review-case write fails.The write retries with the same key. No duplicate case.
T07Three contacts about one unresolved problem, and three about separate enquiries.History tells repeat contacts about one case from separate enquiries.

What the local run actually produced

The integration session ran the whole flow on made-up customers on 3 November. It scored 303 open mortgages. Most look low-risk. 141 cross the normal alert line, but only 6 cross the strict line that matches ten reviews. The model is better than the simple rules, but only moderately good.

Do the top ten really leave more often?

Each month, take the ten highest-scored mortgages. The bars show the share that really refinanced. The dashed line is the normal rate, 22%.

Why this form: two simple charts answer the two questions a sceptic asks: can I trust the percentages, and does the top of the list matter. Trade-off: the 95% margin of error is wide for ten accounts (for the champion, roughly 1.8× to 4.7× the normal rate). It beats the baseline, but the exact multiple is uncertain.

The problem to solve before the demo

Too many alerts for the people available

10

Reviews the team can handle per run (the capacity).

6

Mortgages over the strict line in the checkpoint run. This fits the capacity.

22

Mortgages flagged in each later live run with the earlier threshold (0.5593), per the session report. This was over the capacity.

The strict line was set on checkpoint data, 90 days before the deal ends. Live runs score mortgages at a different point in the deal, so the line no longer fits. The team needs a cap on live alerts, or a separate live threshold. One test fails after extra live runs, so the script runs them only in demo mode.

Update (historical figures above): the threshold now comes from a named rule saved with the model release. The rule is min_precision 0.6, which gives a threshold of 0.5062. The live scores flag 27 mortgages. Every flagged mortgage gets a review case, ranked by score. There is no cap.

How to deploy this to Fabric

A script does most of the work. You sign in once in a browser, and it creates the workspace, publishes the items, uploads the data and runs the notebooks. A few steps stay by hand, mostly because they need an administrator or a person to approve a connection.

What stays by hand, and why

A research check against Microsoft's documentation on 4 November found these cannot be done from a script, or not without extra permissions. The cited pages were not independently re-read.

StepWhy it stays by hand
Purview sensitivity labelsThe API needs an interactive Fabric administrator. It does not accept app identities.
Activator rulesThe script does not build them. The published file format has no way to represent a Power Automate action.
Power Automate flow and its first connectionsA person must approve the SharePoint connection. Linking an Activator rule to a flow is done in the portal.
Free trial capacityThere is no API to start a trial.
One-time tenant settingA Fabric admin must switch on "Service principals can call Fabric public APIs" before an app identity can use the APIs.
Report role membersThey do not travel with the model files. The opt-in rls step can add them, but it needs the model's XMLA endpoint.

Moving to the main workspace

  • Simplest: change the workspace name in the settings and run the script again. It publishes, uploads and trains again, and re-running is safe.
  • Git sync: commit from your workspace to its branch, merge to main, then choose Update all in the main workspace. Git carries item definitions only, not data, trained models or labels. Check the report model file first, because the script writes workspace-specific IDs into it.
  • Deployment pipelines: they also move definitions only, not data.
  • Do not turn on prune while other people share the workspace.

Source: docs/fabric-deployment.md and the PR #10 description. Guidance on moving between workspaces is general Fabric behaviour and is untested here.
